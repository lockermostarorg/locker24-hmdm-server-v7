# Locker24 changes to upstream files

Our own code lives in `plugins/locker24-health`. These are the only upstream files we change. Re-apply them by hand when merging a new upstream release.

| File | Change | Why |
|---|---|---|
| `plugins/pom.xml` | One line in `<modules>`: `<module>locker24-health</module>` | Builds the fleet health plugin with the other plugins |
| `server/pom.xml` | One single-line dependency after `xtra`, in the same one-line format as the other plugins: `<dependency><groupId>com.hmdm.plugin</groupId><artifactId>locker24-health</artifactId><version>0.1.0</version><scope>runtime</scope></dependency>` | Puts the plugin jar into `launcher.war`, where the server finds it at startup |

| `common/src/main/java/com/hmdm/rest/filter/InternalIPFilter.java` | **Upstream security fix** (candidate to send back to Headwind). | `server/src/main/java/com/hmdm/rest/resource/InternalAlertResource.java` | **Upstream security fix** (candidate to send back to Headwind). The constructor also takes `InternalIPFilter`; `triggerAlert` takes `@Context HttpServletRequest` and throws `ForbiddenException` (403) unless `InternalIPFilter.isAllowed(request.getRemoteAddr())`. The Swagger no-arg constructor falls back to a loopback-only filter. Test: `server/src/test/java/com/hmdm/rest/resource/InternalAlertResourceTest.java` | Guice-servlet matches filter patterns against the raw URI, path parameters included, while Tomcat and Jersey strip them: `/rest/internal;x=1/alert` skips the `/rest/internal/*` filter and still reaches this resource (proven in embedded Tomcat 10.1.16). ## Upstream gap: path parameters skip Guice filters

Guice-servlet matches `filter("/rest/xxx/*")` against the raw request URI, including `;` path parameters, while Tomcat and Jersey strip them before routing. So `/rest/private;x/...` skips `JWTFilter`, `AuthFilter` and `PrivateIPFilter`, and `/rest/internal;x/...` skips `InternalIPFilter`, while the resources are still reached. In this fork the only thing that blocks this for `/rest/private/*` is `SpaFilter.hasPathParameters` (`common/src/main/java/com/hmdm/rest/filter/SpaFilter.java`), which answers 400 to any URI containing `;` or `%3B`. That check is load-bearing: never remove `SpaFilter` from `web.xml` or reorder it after `guice-filter`. `/rest/internal/alert` additionally checks the caller in the resource itself (row above). Suggested upstream fix: reject path parameters in the Guice filter chain itself, or check authorization inside the resources, and send both this and the internal endpoint fixes back to Headwind.

Deviations of the health feature from the spec (sections 3.6, 3.7, 4.1) are listed in [`locker24-health.md`](locker24-health.md).
